# ВышКат — учёт парка кикшеринга

Консольное приложение для ДЗ №1 по КПО: доменная модель парка, техосмотр перед приёмкой, отчёты по энергии и списку для новичков, инвентарные номера для техники и вещей. Python 3.10+, SOLID, DI-контейнер ([punq](https://github.com/bobthemighty/punq)), юнит-тесты на pytest.

## Запуск

```
pip install -r requirements.txt
python main.py
```

Тесты и покрытие:

```
pytest
pytest --cov=vyshkat
```

Приложение запускает сценарий-демонстрацию:

1. отчёты по пустому парку;
2. приёмка транспорта (три единицы проходят техосмотр, одна отклоняется);
3. постановка вещей на баланс (шлем, док-станция, зарядный шкаф);
4. отчёты по заполненному парку: количество по типам, суммарное суточное потребление, список для новичков, инвентарные номера техники и вещей.

## Логика решений

- **Две абстракции вместо одной.** `Inventoriable` (номер, название, тип) и `EnergyConsumer` (суточный расход) независимы: велосипед и шлем нужно учитывать, но энергию они не потребляют, а док-станция и самокат делают и то и другое.
- **Транспорт и вещи — разные ветки иерархии.** `Vehicle` проходит техосмотр, `Thing` ставится на баланс сразу. Общее у них только `Inventoriable`.
- **Техосмотр — отдельный сервис.** `FleetService.accept_vehicle` спрашивает `ServiceCenter`, и только при положительном вердикте транспорт попадает в `Fleet`. Отказ возвращается с причиной.
- **Правило «для новичков» — стратегия.** `BeginnerRule` с реализацией `MinScoreRule` (простота ≥ 6). Усложнить правило можно новым классом без правки отчётов.
- **Инвентарные номера** выдаёт `InventoryNumberGenerator` (`VK-0001`, `VK-0002`, …). `Fleet` не допускает дублей.
- **Отчёты только читают** данные парка. Энергия считается по интерфейсу `EnergyConsumer`, а не по списку конкретных классов.
- **Сборка зависимостей** только в `container.py`; остальной код получает зависимости через конструктор.

## Обоснование SOLID

| Принцип | Где и как применён |
|---|---|
| **S** — единственная ответственность | `Fleet` хранит, `FleetService` проводит приёмку, `ServiceCenter` принимает решение по технике, `ReportService` строит отчёты, `InventoryNumberGenerator` выдаёт номера, `ConsoleApp` отвечает за ввод/вывод. |
| **O** — открытость/закрытость | Новый вид транспорта — новый наследник `Vehicle`; новое правило для новичков — новый `BeginnerRule`; новый потребитель энергии — класс с `EnergyConsumer`. `FleetService` и `ReportService` при этом не меняются. |
| **L** — подстановка Лисков | `Scooter`, `Bicycle`, `ElectricBicycle` используются везде как `Vehicle`; `ReportService` и `FleetService` не знают о конкретных типах. Подклассы не ужесточают контракт базового класса. |
| **I** — разделение интерфейсов | `Inventoriable`, `EnergyConsumer`, `BeginnerRule`, `ServiceCenter` — маленькие интерфейсы с одной задачей. Велосипед не обязан реализовывать энергопотребление. |
| **D** — инверсия зависимостей | `FleetService` зависит от абстракции `ServiceCenter`, `ReportService` — от `BeginnerRule`. Конкретные реализации выбираются в `container.py`. |

## Ответы на обязательные вопросы

**1. Какой принцип применён наиболее явно?**
DIP. `FleetService` (`services/fleet.py`) принимает `ServiceCenter` через конструктор, а реализация `BasicServiceCenter` подставляется в `container.py`. Благодаря этому техосмотр заменяется в тестах без правки сервиса. Также явно виден ISP: `Inventoriable` и `EnergyConsumer` в `domain/abstractions.py`.

**2. Какой принцип сознательно ограничен?**
SRP. `Fleet` хранит и транспорт, и вещи в одном классе, хотя можно было бы разделить на два репозитория. При текущем объёме (два списка и проверка уникальности номера) разделение дало бы лишние классы без пользы, то есть overengineering. Если появятся станции и склад запчастей, `Fleet` стоит разделить. Ещё один компромисс: `ReportService.total_energy_kwh` использует `isinstance(item, EnergyConsumer)`, но проверяет интерфейс, а не конкретные классы, поэтому OCP не нарушается.

**3. Что сломается при расширении?**
- *Новый вид транспорта* (например, моноколесо): добавляется класс-наследник `Vehicle` в `domain/vehicles.py` (и `EnergyConsumer`, если он электрический). `Fleet`, `FleetService`, `ReportService`, `ServiceCenter` не меняются. Ничего не сломается.
- *Сотрудник*: не наследует `Inventoriable`, поэтому не попадёт на баланс и в отчёты; парк не затрагивается. Понадобится отдельная модель и сервис.
- *Склад запчастей*: запчасть — наследник `Thing`, и `Fleet.add_thing` с отчётами работают сразу. Для самого склада (остатки, перемещения) нужен новый сервис, а текущий код не меняется.
- Единственное, что придётся поправить вручную, — демонстрационный сценарий в `console.py`, если новые сущности нужно показать.

**4. Какой тест фиксирует решение техосмотра и правило для новичков?**
- Техосмотр: `test_vehicle_added_when_inspection_passed` и `test_vehicle_not_added_when_inspection_failed` в `tests/test_fleet.py`. Зависимость подменяется через `Mock(spec=ServiceCenter)`, который передаётся в конструктор `FleetService`. `test_container_uses_substituted_service_center` проверяет подмену через DI-контейнер: `build_container(service_center=fake)`.
- Пороговое значение техосмотра: `test_basic_service_center_threshold` в `tests/test_inspection.py` (69 — отказ, 70 — принят).
- Правило для новичков: `test_min_score_rule_boundary` в `tests/test_beginner_rules.py` (5 — нет, 6 и 10 — да) и `test_beginner_vehicles_follow_rule` в `tests/test_reports.py`.

**5. Что сделал ИИ**
С помощью ИИ был оформлен отчет и сделаны тесты на основе кода и требований. По ходу работы была консультация и разбор ошибок ручного кода с ИИ помощником.
